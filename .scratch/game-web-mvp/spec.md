# Spec: 血色牌局 Web 版 MVP

Status: ready-for-agent

## Problem Statement

《血色牌局》是一款构筑式扑克策略桌游（1-8人），但对局需要实体配件、凑人困难、洗牌发牌繁琐。团队希望在 web 上随时开局：不依赖实体卡牌，触屏与鼠标设备都能玩，内部成员可快速约局，单人时也能与机械荷官对局。

## Solution

构建一个 web 线上版《血色牌局》：TS monorepo（engine / server / web 三包），服务端权威状态机通过 WebSocket 同步，docker-compose 双服务部署（nginx 静态前端 + Node 后端）。MVP 覆盖三种模式：标准局（2-4 人）、简易模式、单人模式（机械荷官 + 命运牌）。无账号系统，昵称 + 房间码进入。卡牌图片资源与效果文本逐步接入，先以占位卡渲染。

## User Stories

1. 作为玩家，我想输入昵称创建或加入房间，以便无需注册快速开局。
2. 作为房主，我想通过分享链接/房间码邀请朋友，以便省去口头传码。
3. 作为房主，我想在开局前配置模式（标准/简易/单人）、玩家人数与规则选项，以便适配不同局。
4. 作为玩家，我想在抽牌阶段自动抽至手牌上限（默认6张），以便不用手动数牌。
5. 作为玩家，我想在换牌阶段弃置至多3张并补抽，以便优化手牌。
6. 作为玩家，我想把未使用的换牌次数自动兑换成血筹，以便不漏掉这条规则。
7. 作为玩家，我想在出牌阶段从手牌暗选5张放入出牌区，以便其余玩家看不到我的选择。
8. 作为玩家，我想在对决阶段按"临时特权证→顺时针"顺序逐项宣告（JOKER赋值、牌型、技能、芯片），以便策略性隐藏/展示信息。
9. 作为玩家，我想让系统自动计算我的最大牌型与总点数，以便不用人工记牌型表（七条/同花六条/六条/同花五条/同花葫芦/同花顺/五条/四条/葫芦/同花/顺子/三条/两对/一对/高牌）。
10. 作为玩家，我想在牌型相同时自动比较总点数、再相同时按特权证距离判胜负，以便裁决无争议。
11. 作为玩家，我想在结算阶段自动获得排名奖励（车票+血筹），以便不用查表。
12. 作为玩家，我想在购买阶段从黑市区5格购牌并自动补位，以便体验黑市构筑。
13. 作为玩家，我想把强化芯片插入弃牌区的牌（每牌限1枚、点数范围2-14校验），以便改造牌库。
14. 作为玩家，我想把备用道具放入道具区并在之后使用一次，以便囤积关键道具。
15. 作为玩家，我想让秘密交易类黑市牌立即结算，以便不占用道具区。
16. 作为玩家，我想在删牌阶段免费删1张、付费2血筹/张追加删牌，以便精简牌库。
17. 作为玩家，我想在重整阶段选择"重洗牌库"或"获得2血筹"，以便管理牌库质量。
18. 作为玩家，我想在抽牌堆不足时自动洗混弃牌堆重组，以便牌库永远够用。
19. 作为玩家，我想查看自己的弃牌区与删牌区，但不能看他人的，也不能看任何抽牌堆，以便保留信息博弈。
20. 作为玩家，我想看到所有人的血筹与车票数量（公开信息），以便做资源决策。
21. 作为2人局玩家，我想以24票为目标、按"第一名4票/第二名4筹"结算，以便快速对局。
22. 作为3人局玩家，我想以20票为目标、按"4票/2票2筹/4筹"结算。
23. 作为4人局玩家，我想以16票为目标、按"4票/2票2筹/1票3筹/4筹"结算。
24. 作为运营者，我想把排名奖励表做成配置文件，以便调难度不改代码。
25. 作为玩家，我想在结算阶段有人达标时立即结束游戏并按票数→筹码→特权证距离排出名次，以便清晰分出胜负。
26. 作为玩家，我想在角色抽选时"抽2选1"并公示角色技能，以便策略选角。
27. 作为玩家，我想在初始构筑时抽8张并删除至多4张（公示），以便定制开局。
28. 作为玩家，我想在点数比较中让A恒为14、最小顺子23456、最大顺子10JQKA，以便规则一致。
29. 作为玩家，我想让JOKER仅在对决阶段可视为任意点数花色，以便符合"金科玉律"。
30. 作为玩家，我想让强化芯片永久绑定、不可拔除替换，被删牌连芯片一起进删牌区，以便规则不被钻空子。
31. 作为玩家，我想让效果冲突按"事件牌>角色技能>黑市牌>规则书"优先级结算，以便多方效果可控。
32. 作为玩家，我想让"特殊效果优先于一般规则"，以便卡牌文本覆盖规则书。
33. 作为新手玩家，我想用简易模式开局（固定4角色、无初始构筑、移除J/Q/K/A、仅黄色边框黑市牌、无免费删牌），以便快速上手。
34. 作为单人玩家，我想3选1挑战机械荷官（Doloris/Timoris/Mortis），以便体验不同节奏压力。
35. 作为单人玩家，我想在对决阶段掷骰子决定荷官牌型（命运牌上的？位、1视为A），以便对抗命运。
36. 作为单人玩家，我想让荷官血筹无限、荷官效果优先，以便符合单人规则。
37. 作为单人玩家，我想在荷官未夺魁时从高级命运牌库补牌进基础库，以便难度递增。
38. 作为单人玩家，我想率先达到24票获胜、荷官先达标则失败，以便目标明确。
39. 作为掉线玩家，我想重连后接管自己被托管的操作，以便网络波动不毁局。
40. 作为其他玩家，我想让掉线/超时玩家被系统按最小操作原则托管（不换牌/出最高牌型/不购买/不删牌），以便不等人。
41. 作为触屏玩家，我想所有操作（选牌、拖拽、确认、宣告面板）都可用手指完成，以便手机开局。
42. 作为桌面玩家，我想用鼠标完成同样操作，以便办公室游玩。
43. 作为玩家，我想看到未提供图片的卡牌以"卡名+分类色块+效果文字"的占位卡渲染，以便先玩起来不等美术。
44. 作为开发协作方，我想按"卡牌ID→文件名"约定投放图片即自动生效，以便逐步替换占位图。
45. 作为运营者，我想把角色/黑市牌/命运牌定义为 JSON 数据（名称/价格/类型/颜色分类/效果ID/图片路径），以便卡池持续扩充。
46. 作为玩家，我想看到当前阶段、各玩家就绪状态与倒计时，以便知道谁卡住了流程。
47. 作为玩家，我想在购买阶段看到最右两格黑市牌上的叠加血筹并可随牌购得，以便理解黑市补贴机制。
48. 作为玩家，我想让黑市被买空时不再补齐、用剩余牌继续，以便极端情况有明确行为。
49. 作为玩家，我想在角色牌箭头处看到剩余换牌次数（超4次部分另行记忆/显示），以便跟随实体规则。
50. 作为开发维护者，我想让所有效果以 TS 函数注册进效果注册表（触发时机+执行逻辑），以便新增卡牌只加不改。

## Implementation Decisions

- **仓库结构**：TS monorepo，三包：`engine`（纯 TS 游戏引擎，无 IO 依赖，前后端共用）、`server`（Node + WebSocket，服务端权威状态机，SQLite 仅存牌局记录/复盘数据，房间活跃状态在内存）、`web`（React + Vite）。
- **服务端权威**：客户端只做渲染 + 提交操作；所有状态变更由服务端引擎执行并广播 diff/快照。不考虑反作弊，但多人同步本身要求服务端权威；单人模式的荷官引擎同样跑在服务端，复用同一 engine。
- **同步协议**：WebSocket 房间模型。客户端断线重连用昵称 + localStorage 临时身份令牌；重连后全量快照恢复。
- **效果系统**：不做 DSL。引擎实现"阶段前/中/后"时间点框架 + 优先级链（事件牌>角色技能>黑市牌>规则书，同时机按特权证→顺时针）；每张牌的效果是注册进注册表的 TS 函数。卡池数据 JSON 化（含未来扩充），效果函数按卡牌 ID 注册。
- **卡牌数据管道**：定义统一 JSON 模板（id/名称/价格/类型/颜色分类/效果ID/效果文本/图片路径）；协作方提供 Excel 或文本，由开发侧转换为 JSON。首批牌池 = 简易模式 4 角色 + 黄色边框黑市牌。
- **占位渲染**：图片缺失时前端按"卡名 + 分类色块 + 效果文字"渲染占位卡；图片按 ID→文件名约定放入目录即生效，无需改代码。
- **宣告阶段**：半结构化——系统计算基础牌型，JOKER 赋值、技能发动、芯片使用逐项弹出选择面板，玩家按特权证→顺时针排队逐个确认。
- **托管**：掉线或出牌超时（默认 120 秒，可配置）进入托管，按最小操作原则自动执行；重连接管。
- **排名奖励表**：配置文件驱动（按玩家人数分档，数值已确认：2人局 4票/4筹；3人局 4票/2票2筹/4筹；4人局 4票/2票2筹/1票3筹/4筹），便于调难度。
- **UI 基色**：暗色牌桌风。血红主色 `#e9404b`、暗红 `#583c42`、提示框金 `#ffc840`，围绕三色延伸完整色阶（背景层级、按黑市牌颜色分类的卡边框、状态色）。横屏最优，触屏与鼠标共用布局与交互。
- **部署**：docker-compose 双服务：`web`（nginx 静态资源 + 反代 `/ws`）、`server`（Node）。SQLite 数据卷持久化。
- **规则细节锚点**（实现时以规则书为准）：手牌上限6；换牌默认3次、持特权证4次；A=14；顺子 23456~10JQKA；六条/七条/同花五条等"造出的牌型"合法且仅取单一最大牌型；黑市购买回合结束在最右两格叠1血筹；删牌免费1张+2血筹/张；重整二选一；抽牌必须一次抽完；血筹为公开信息。

## UI 与交互决策（源自 05 原型 v4，2026-08-29 飞飞拍板为基线，后续打磨另开票）

> 完整原型：`.scratch/game-web-mvp/prototypes/table-ui.html`（假数据驱动）。以下是实装必须遵循的交互契约。

### 布局（实体牌桌隐喻，横屏最优）
- **中央**：黑市区 5 格（价格、叠加血筹角标、效果文本、分类色边框、供应堆张数）。
- **四向座位**：上/左/右三个对手 + 底部自己；每个座位旁有**独立出牌区**（座位与中央之间，即玩家"面前"），牌面按座位方位旋转（上 180°、左 90°、右 -90°）。
- **座位信息牌**：角色牌缩略卡 + 车票计数（x/目标）+ 血筹 + 换牌次数 已用/上限（特权证 4）+ 牌库剩余张数 + 手牌牌背数；已结束阶段的玩家显示"✓ 已结束"标记。
- **个人操作台（底部，两行结构）**：
  - 第一行 = 昵称+徽标 + 操作按钮（右对齐、横向排列）；
  - 第二行 = 阶段提示（≥14px）+ 全员结束进度 x/n；
  - 下方：手牌横滚区 + 牌堆/弃牌堆分区（各标张数、叠层视觉）+ 道具区（备用道具带"使用"按钮）。

### 阶段推进机制（程序控制，联动引擎 endPhase Action）
1. 顶栏步进条为**只读**指示器（回合数 + 8 阶段 + 目标票数），阶段流转由"全员结束标记"驱动，客户端不可点跳。
2. 每个阶段操作区有**"结束阶段"按钮**（抽牌/结算等自动阶段确认后即可结束）；点击后自己打上结束标记，不能再操作手牌（拦截提示）。
3. 结束标记通过快照同步给所有玩家（座位牌 ✓ 标记 + 浮现动画）；操作区实时显示"全员进度 x/n"。
4. 服务端收齐全员 endPhase 后自动推进下一阶段；回合末自动进入下一回合抽牌。
5. **转场强提示动画**：阶段切换时全屏暗化 + 大字"XX阶段 / 第N回合"弹出（血红描边+金色大字），约 1 秒后自动缩小飞入顶栏对应指示格，无需交互。
6. 特例：出牌暗扣后仍需手动"结束阶段"（体现同步等待）；对决阶段全员完成宣告即视为结束。

### 各阶段交互形态
- 换牌：点选手牌→换牌按钮（≤3 张），"停止换牌"一键兑血筹；剩余次数实时显示。
- 出牌：选满 5 张才能暗扣（按钮锁定防误触）；确认后手牌**飞向自己出牌区**（出牌飞行动画），他人出牌浮现于其出牌区。
- 对决：**宣告面板**——按"特权证→顺时针"宣告队列（1.你 → 2.对手…）+ 三步逐项确认（JOKER 赋值选项 → 技能发动/不发动 → 芯片使用），完成后自动滚到下一位宣告者，最后展示结算日志；JOKER 候选由引擎求解器提供。
- 购买：点黑市卡购买，买后右侧补位推进，叠加血筹随牌取走；**芯片插入弹窗**：选弃牌区目标牌、点数越界自动置灰、插入后牌角芯片标记。
- 删牌：弹窗选弃牌区牌，第 1 张免费、后续实时显示累计费用、血筹不足拦截。
- 重整：二选一按钮（重洗 / +2 血筹）。

### 通用交互
- **头像可点击**：所有玩家头像弹出该玩家角色名 + 技能描述（文本来自卡池数据）。
- 断点适配：宽度 ≤860px 缩卡布局；新增 **max-height ≤560px** 压缩断点（横屏手机等高度紧张设备），压缩顶栏/座位牌/黑市卡/手牌/按钮/转场大字。
- 触屏与鼠标共用布局，点击目标 ≥44px。
- 占位卡：卡名+点数花色+效果文本直接可读，不依赖美术资源。

### 视觉
暗色牌桌，三基色延伸：血红 `#e9404b`（行动按钮/当前阶段/筹码）、暗红 `#583c42`（面板系）、提示金 `#ffc840`（焦点/徽标/提示）。黑市牌分类描边：经济金/删牌紫/容错蓝/互动暗红/牌型绿。

## M3' 批次增补（2026-08-30 grilling 定稿，单人模式暂缓）

> 2026-08-30 与飞飞 grilling 两轮定稿。本批次落地"标准局完整可玩 + 卡牌图片 + 芯片可视化 + 暗扣交互式声明 + 自动化集成测试 + CI"；**单人模式（机械荷官 + 命运牌）暂缓**——机械荷官未提供，票据保留但标记暂缓。变体（捣蛋鬼/组队/暗藏杀机/列车事件/事件牌）维持排除，事件牌数据已入管道但 handler 降级"无效果+log"。

### 范围决策
- **模式**：标准局（2-4 人）完整落地（抽 2 选 1 角色、初始构筑、全量 105 黑市牌）；简易模式保持完整；单人模式暂不实现。
- **效果真身化**：17 张标准角色、28 张非黄边黑市牌的占位效果全部实现真身，含 hand-evaluator 芯片视图、【临时特权证】状态、黑市区 slot 交互等 M2 遗留。

### 卡牌图片上图
- web 卡面按 config JSON 的 `image` 字段（`assets/cards/<类>/<ID>.png`）加载真实图片；加载失败回退现有占位渲染（卡名+分类色块+效果文本）。扑克牌与黑市/角色卡统一走该逻辑。

### 元数据下发（芯片详情前置）
- server 向客户端下发卡池元数据（黑市牌名、分类、效果文本、角色技能文本），web 替换 defId 裸显示。
- 顺带清 M2 遗留：终局写 SQLite 局摘要（spec 既定承诺）。

### 芯片可视化（显示规则，飞飞确认）
- **标记**：插过芯片的手牌/出牌区卡面显示芯片角标（金色徽标）。
- **详情**：点击卡牌弹芯片详情面板——芯片名称 + 效果文本（依赖元数据下发）。
- **数值芯片**：卡面主数字显示修改后点数，括号内显示「基础点数+芯片加值」，如基础 5、芯片 +4 → `9 (5+4)`。
- **花色声明**：改花色类芯片在卡面括号提示，如 `♠(原♥)`。
- 括号内**只反映芯片贡献**，角色技能等其他加成在宣告面板体现，避免括号变算术黑洞。

### 暗扣交互式声明（飞飞确认）
- **出牌阶段**提交 5 张暗扣时，若所出牌带声明类芯片（改花色/声明牌型等），立即弹出交互面板选择声明值，随 playCards 动作一起提交落库；**宣告阶段自动按规则顺序展示**（点数花色→最大牌型→芯片效果→技能→道具），不需玩家再操作。
- **六/七条放宽**：出牌阶段若手牌中芯片可满足六条/七条，个人手牌区显示提示，选牌上限从 5 放宽到 6/7；引擎 playCards 校验同步放宽（上限=5+可造额外条数，仍受手牌张数约束）。

## Testing Decisions

- **唯一核心 seam：`engine` 包的公开 API**。引擎是纯函数式状态机（输入：当前状态 + 操作/事件 → 输出新状态 + 效果队列），不依赖 IO。绝大多数测试打在这个 seam 上：给定牌局状态与玩家操作，断言状态转移、牌型判定、结算数值、优先级顺序。这是最高可测 seam，不需要 mock 任何外部设施。
- **次级 seam：server 的 WebSocket 消息契约**。少量集成测试验证"客户端操作消息 → 引擎调用 → 广播快照/diff"的协议转换与断线重连，不测 UI。
- **好的测试**：只断言外部可观察行为（状态、奖励数值、胜利判定），不断言内部调用结构。规则书中的示例（如"特型演员 vs 矿工"葫芦对决 39 vs 46 点）直接作为验收用例。
- **先例**：仓库尚无测试先例，engine 测试是该仓库测试文化的起点，用 Vitest。
